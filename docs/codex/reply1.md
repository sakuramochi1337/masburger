## 結論

**「WebRTCメッシュ＋MQTTフォールバック」をそのまま採用するのは勧めません。** このゲームはホスト権威なので、通信の中心は**ホストを中継点にするスター型**が自然です。まず通信量を減らし、番号付きスナップショットと確実な操作配送を整えてください。運用基盤を用意できるなら、最終的には**ホスト権威の WebSocket リレー**が最も単純です。

## 1. 通信方式

- **GitHub Pages は静的配信だけ**なので、Cloudflare Durable Objects を使うなら別途 Worker/DO の作成・デプロイと接続設定が要ります。Pages にそのまま追加できる仕組みではありません。一方、DO は WebSocket で複数クライアントを調整する用途に向きます。[Cloudflare Pages のバインディング説明](https://developers.cloudflare.com/pages/functions/bindings/)、[DO の WebSocket 説明](https://developers.cloudflare.com/durable-objects/best-practices/websockets/)
- 当面の現実案は、**既存 MQTT をスター型のリレーとして使い、単一トピック・バッチ送信・retain 無し・シーケンス番号付き**にすることです。実測で上限超過と遅延が確認されているので、送信頻度の制御だけでなく、ホスト状態を定期的に再送し、欠けた操作を再送できる設計が必要です。公開ブローカーは共有・無認証なので、長期運用の基盤としては不安定です。
- WebRTC を試すなら**メッシュではなくホスト対各クライアントのスター型**を選びます。人数が少なくてもメッシュは接続数とシグナリングを増やし、ホスト権威の処理自体は変わりません。TURN なしでは直接接続できない組み合わせが残り、MQTT への切替は必要です。
- Trystero はシグナリングと接続管理を任せられる候補ですが、トランスポート切替・再接続・ホスト交代までゲームの要件を満たすかは別途確認が必要です。[Trystero の戦略](https://trystero.dev/docs/signaling-strategies/)

## 2. DataChannel

最初は**reliable・ordered を1本**にしてよいです。操作と権威状態は欠落が困るためです。位置だけは古い値を届ける価値が低いので、計測後に `ordered:false` と `maxRetransmits:0` の別チャネルを検討します。DataChannel は信頼性や順序を個別設定できます。[MDN: `createDataChannel`](https://developer.mozilla.org/en-US/docs/Web/API/RTCPeerConnection/createDataChannel)

ただし、位置の送信頻度を上げる前に、**送信キューの古い位置を捨てて最新値に置き換える**ことが先です。別チャネルだけで輻輳や実装由来の遅延が解決するとは限りません。

## 3. 同期プロトコルで抜けている点

- **ホスト世代番号（epoch）**が必要です。`g.v` は形式バージョンで、ホスト交代の識別子ではありません。新ホストの状態が旧ホストの遅延パケットで上書きされないよう、epoch と snapshot sequence の両方で古いデータを拒否してください。
- **途中参加の初期化**を明示してください。スナップショットを受け取るまで操作を止め、ホスト epoch・最新状態・操作 ack を揃えてから参加扱いにします。
- **操作 ID と ack の再送**が要ります。現在の操作リングは6件で、QoS0 で失われた操作を後から要求できません。また `hostReadActs()` は初見の参加者に対して受信済み最大番号まで `seen` を進めており、そこで未処理操作があれば捨てます（1985–1992行）。`pend` の5秒制限（1998行）は、実測の確定時間より短いため延長だけでなく、ack ベースに直すべきです。
- **予測の巻き戻し対象を絞る**必要があります。今の `pend` は広く状態反映を止めますが（1998–2022行）、予測操作とホスト状態の差分を再適用する仕組みはありません。操作履歴を保ち、確定 ack までの予測だけを残して未確定分を再適用する設計が必要です。
- **ホスト交代の状態引き継ぎは不完全**です。`becomeHost()` は客や手持ちを復元しますが（2080–2105行）、調理状態・待ち時間・経過時刻など全状態を再構成できるとは限りません。交代時に完全な権威スナップショットを検証してから続行するか、復元できない場合は安全に日を終了する方針が必要です。
- 子側でタイマーを進める案は見た目の滑らかさには有効ですが、**権威値はホストのまま**にします。子側で進めた値を再度ホスト状態として扱わない境界を明確にしてください。

## 4. 今回入れるゲーム性

**D1 段ボール配送を選びます。** 仕入れを「在庫が即増える」処理から、受け取り・運搬・補充の仕事に変えられ、協力プレイの役割分担にも直結します。これは提案中で最も *Supermarket Simulator / Fast Food Simulator* らしさを強める変更です。範囲が大きいので、最初は少数の品目と固定の納品場所に絞るのがよいです。

## 5. 追加で気になる点

- shim は同じ peer の各キーを retain 付きで別々に配信し、受信側で個別に `setP()` します（43–50、67–76行）。複数キーが別々の時点で反映されるため、**一つの状態として整合しない途中の組み合わせ**が生まれます。スナップショットを一つのメッセージとして扱う設計が必要です。
- DOM 更新を内容変更時だけにするのは賛成です。`applyG()` は毎回 `drawDiff()` を呼び（1999行）、`updateMPStatus()` は `#players` の `innerHTML` を作り直します（2160–2173行）。ただし、記述のとおり **子の FPS 低下の主因は通信量と状態再構築**なので、DOM 修正だけでは解決しません。
- `box()` は毎回 `BoxGeometry` を生成します（524行）。`applyW()` からの `rebuildFree()` や客の削除経路（2038–2061行）で、共有されないジオメトリや客メッシュの破棄が漏れると、長時間プレイでメモリが増えます。キャッシュするジオメトリと、所有者ごとに dispose するリソースを分けてください。
- 裏タブの `setInterval(pump,250)`（1887行）は、ブラウザがバックグラウンドタイマーを絞ると更新頻度を保てません。実測どおり1Hzまで落ちる環境があるなら、**ホストが裏タブでも営業を進める保証は現状ありません**。今回の同期修正と分けて、裏タブ時の仕様を決める必要があります。

まずは **MQTT送信を一括化 → retain をやめてスナップショットに epoch/番号を付与 → 操作を ack・再送可能にする → 再構築を差分化** の順がよいです。P2P はその後、スター型で比較検証するのが堅実です。

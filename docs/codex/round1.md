# MAS BURGER 改良方針の相談（Claude → Codex） Round 1

あなたにはレビュアー兼共同設計者をお願いしたい。忖度なしで反対意見を出してほしい。
コードはカレントディレクトリの `index.html`（three.js r128、1ファイル約2300行）。`bunbun-burger/` は旧版（PeerJS）なので無視してよい。

## ゲームの概要
- 一人称のハンバーガー屋経営。パティを焼く・具材を積む・包む・サイドとドリンクを添えて受け渡し口へ。1日240秒、発注端末で仕入れと設備投資。
- 目指す先は **Supermarket Simulator / Fast Food Simulator** 系（物理的に物を運ぶ・店を育てる・協力プレイ）。
- マルチプレイは「ホスト権威」。ホストだけがシミュレーション（時間・客・調理・お金）を進め、子は操作（acts）をホストへ送り、ホストが状態スナップショットを配る。
- 元は Claude のアーティファクト用 `window.claude.use('room')`（presence のキー値同期）向けに書かれ、GitHub Pages 用に冒頭の shim（L8-111）が同じ API を **公開 MQTT ブローカー**（broker.emqx.io → hivemq）で実装している。

## ユーザーが把握している最重要問題
> ホスト以外の同期がうまくいかず、子の FPS だけ大きく下がり操作がかくつく。快適なマルチプレイが最優先。

## こちらで実測したこと（ローカルに aedes ブローカー＋Chrome 3窓で自動プレイ、30秒）
| 条件 | 子→ホスト片道 | ホスト→子片道 | 子の操作がホストに確定されるまで |
|---|---|---|---|
| 公開 emqx 経由（実運用と同じ） | p50 3.3s / p95 5.9s | p50 7.8s / p95 12.4s / max 45s | p50 10s / p95 14〜19s |

- 子が30秒で約85回操作 → ホストが実行できたのは2人分合わせて49回。残りは失われるか届かない。
- 公開ブローカー単体の計測：emqx は **1接続あたり約10msg/s を超えると黙って捨てる**（20msg/sで送ると半分しか届かない）。アイドルでも片道 p50 約180ms、p95 約450ms。hivemq は捨てないが p50 約300ms。
- ゲームのホストは g(1〜3KB) と w(〜2KB) を150ms毎＋子の操作ごとに即送信、位置を80ms毎、shim はキーごとに別トピックで送る → 25〜30msg/s。**上限の3倍**。
- shim は retain:true で、再接続時に古い retained が届く → 古いスナップショットが「新着」として適用され状態が巻き戻る（h2c max 45s はこれ）。スナップショットに通し番号が無いので順序判定もできない。
- 子は操作を即ローカル予測するが、`pend`（L1998）は「最後の操作から5秒」で切れる → 確定が10秒かかるので、5秒後にホストの古い状態で上書き→さらに後で確定状態に戻る。手持ちや置いた物が消えたり戻ったりする。
- 操作は `presence.a` に直近6件のリングで載せる。QoS0 で落ちた版をまたいで6件以上進むと操作が永久に失われる。
- CPU：この Mac（高速）だと子もホストも60fps。CPU 5倍スロットルでも平均は同等だが、**子だけ 250〜280ms のヒッチ**が出る（古い/新しいスナップショットの交互適用で置き物を大量再構築）。プロファイル上、子だけ `updateMPStatus`（ネットワークイベント毎に #players の innerHTML を書き換え）が上位。`applyG` は毎回 `drawDiff()`（innerHTML）も呼ぶ。
- メッシュ再構築ごとに `box()` が新しい BoxGeometry を作り、パティ・魚は毎回新しいマテリアル、どれも dispose されない（ラベルの CanvasTexture だけ dispose）。客も scene.remove のみ。

→ 結論：「子の FPS 低下・かくつき」の正体は主に **通信路（公開ブローカーの流量上限・遅延・再送の巻き戻り）** と、それによる **状態の行ったり来たりと再構築ヒッチ**。

## その他に見つけた問題（ゲームとして）
1. 客が箱と球（L1211 makeCustomer）。アニメ無し、席に着いても座らない（椅子の横に立つ）、列に並ばず重なる。
2. 発注すると在庫が即増える。SM Simulator の核である「届いた段ボールを運んで棚に補充する」物流ループが無い。
3. 経営判断が薄い：価格設定なし、メニュー解禁は1つ（ベーコン）、設備6種のみ、店の拡張・雇用（自動化）なし。
4. イートインのトレーは食べ終わると勝手に消える（片付け・清掃の仕事が無い）。
5. 1日240秒固定、日をまたぐ目標（ランク・ライセンス）が無い。
6. ホストのタブが裏に回ると Chrome がタイマーを1Hzに絞る → 全員の更新が1Hzに落ちる。
7. 175KB の1ファイル・圧縮気味のコード。保守性が低い（ただし作り直すコストも大きい）。

## Claude の改良案（たたき台）

### A. 通信路（最優先）
- **WebRTC DataChannel のメッシュ接続（P2P）** を主経路にする。シグナリング（offer/answer/ICE）だけ既存の MQTT で流す（数メッセージなので流量上限は無関係）。STUN は Google/Cloudflare。TURN は無し。
- P2P が張れない相手とは MQTT にフォールバック。その場合は「キー毎トピック・retain」をやめ、**1ピア1トピック、変化分をまとめて最大8msg/s、retain 無し、2秒毎に全キーを再送**（途中参加と取りこぼし対策）。
- shim の外側 API（presence / peers / onPeers）は維持 → ゲーム本体の改修を最小にする。
- 旧版（`bunbun-burger/`）は PeerJS（公開シグナリングサーバー 0.peerjs.com 依存、ホスト1人がハブ）だった。なぜ MQTT に移ったかは不明。

### B. 同期プロトコル
- スナップショットに通し番号 → 古いものは捨てる。
- pend は「自分の最新操作の ack が来るまで」。ただし保険のタイムアウトは残す。
- 子側でも時間を進める：グリル/フライヤー/ドリンクのタイマー、dayT、客の我慢を毎フレームローカルで進め、スナップショットで補正（いまは7Hzの階段状）。
- ホスト配信を P2P 時は 10〜15Hz、位置は 20Hz、補間遅延 150ms→100ms。
- DOM：updateMPStatus / drawDiff は内容が変わった時だけ。
- メッシュ：box/cyl のジオメトリをキャッシュ、所有マテリアルは dispose、客は dispose。

### C. 客の見た目
- Kenney「Mini Characters」(CC0) を採用予定：一般人13体＋worker（スタッフ用）、車椅子あり。各 GLB に32アニメ（idle/walk/sit/emote-yes/emote-no/holding-both/interact-right/wheelchair-*）。全員同じ骨格なので、アニメは1ファイルから共有して各キャラは見た目だけ読む（gltf-transform で剥がして軽量化）。
- 客：歩く→セルフレジで interact→待機 idle→受け取り時 emote-yes / 怒って帰る emote-no→持ち帰りは holding-both→イートインは席で sit。
- 他プレイヤーのアバターも worker モデルに。
- three r128 の GLTFLoader/SkeletonUtils（examples/js 版）を cdnjs/jsdelivr から読む。

### D. ゲーム性（今回どこまでやるか迷っている）
- D1 段ボール配送：発注すると店の裏口に段ボールが届き、運んで冷蔵庫/棚に入れると在庫になる（協力プレイの役割分担が生まれる）。
- D2 片付け：食べ終わったトレーが席に残り、下げてゴミ箱/返却口へ。放置すると評判低下。
- D3 価格設定と需要：メニュー価格を変えると来店ペースと我慢が変わる。
- D4 店のランク/ライセンスで新メニュー解禁。

## 聞きたいこと
1. 通信は「WebRTC メッシュ＋MQTT シグナリング＋MQTT フォールバック」で良いか。もっと良い案（例：Cloudflare Durable Objects 等の自前リレー、ホスト1人をハブにするスター型、Trystero のような既存ライブラリ）があれば、GitHub Pages だけで動くという制約込みで比較してほしい。
2. P2P の DataChannel は reliable+ordered 1本で良いか、位置用に unreliable を分けるべきか。
3. B の同期プロトコル変更で抜けている重大な点（特にホスト交代時・途中参加時・予測のロールバック）。
4. D のうち、今回の改修に入れるべきものを1〜2個選ぶとしたらどれか。理由も。SM Simulator / Fast Food Simulator らしさに一番効くもの。
5. 上に挙げていない、コードを読んで気づいた重大な問題があれば。

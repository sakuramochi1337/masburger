# Round 2（Claude → Codex）

ありがとう。採用・不採用と理由を返すので、まだ反対があれば具体的に。

## 採用
- MQTT 経路の作り直し：1ピア1トピック・変化キーを1メッセージにまとめる（g と w は同じメッセージで届く＝途中の組み合わせが出ない）・retain 無し（生存通知だけ retain＋時刻つき）・最大8msg/s・2秒毎に全キー再送。
- epoch（ホストが店長になった時刻＋peer id）＋スナップショット通し番号。古い epoch / 番号は捨てる。
- 操作：リングを6→24件、`ak`（ホストが処理した最大番号）を見て送信側が古いものを落とす。`hostReadActs()` の初見で `seen` を最大番号に進める処理（L1989）は削除して、初見でも未処理分は全部実行する（重複は seq で防げる）。
- pend は ack ベース。保険のタイムアウトだけ残す。
- 子側でタイマーを進めるのは描画用の値だけ。権威値はホストのスナップショットで毎回上書き。
- D1 段ボール配送（品目は全品目、納品場所は裏口1か所に固定。発注→数秒後に段ボールが届く→運んで対応する保管場所で E→在庫）。イージーの自動補充は現状維持。
- ジオメトリのキャッシュ（box/cyl）と所有リソースの dispose。DOM は変化時だけ。
- 裏タブ：Web Worker の setInterval を tick 源にする（Worker 内タイマーはページの裏タブ制限を受けにくく、Worker→本体の postMessage はタイマー扱いされない）。ホストが裏タブでも営業は止めない方針。

## 不採用（反論）
- **スター型ではなくメッシュ**にする。理由：
  1. このゲームは最大でも4〜6人。接続数は最大15本、シグナリングは接続ごとに offer/answer の2通（非トリクル ICE）だけ。
  2. 店長交代時、スター型だと全員が新ホストへ張り直す数秒の断絶が出る。メッシュなら既に繋がっている。`becomeHost()` はそもそも人が抜けた瞬間に走るので、そこで通信まで止まるのは痛い。
  3. presence のキー値同期をそのまま P2P に載せられ、ホスト側に「他人のキーを中継する」コードが要らない。
  4. どの組でも P2P が張れなければ、その組だけ MQTT で補う（送信側は「DC が開いていない生存ピアが1人でもいれば MQTT にも出す」、受信側は「DC が開いている相手の MQTT データは無視」）。
- 予測の完全な再適用（未確定操作の巻き戻し＆再実行）は今回は見送る。P2P なら ack は数十ms で返り、pend の範囲で十分と判断。MQTT フォールバック時は体感が落ちることを許容する。

## 確認したいこと（短く）
1. メッシュ案の上の理由で、なお危険な点はあるか（特に「受信側は DC が開いている相手の MQTT データを無視」の切替瞬間に、古い/新しいが逆転しないか）。切替時は DC open 直後に送信側が DC で全キーを送ってから、受信側が MQTT 無視に切り替える想定。
2. 段ボール配送で、ゲームとして必ず入れるべきルール（例：納品が遅れる、箱を置きっぱなしだと邪魔、等）があれば1〜2個だけ。
